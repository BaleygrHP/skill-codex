## 1. Artifact model

Each project owns an independent workflow root. By default, tickets live in `Issue/` and Flows live in sibling `FLOW/`, but tools must read `.ticket-workflow.json` and preserve repository-local paths.

```text
RULE.md
.ticket-workflow.json
Issue/
  README.md
  _TEMPLATE/
  TD000001/
    README.md
    spec.md
    discuss.md
    diff-note.md
    review.md
    outscope.md
FLOW/
  _TEMPLATE/
  FL000001/
    flow.md
    current-wave.md
    review-queue.md
    decision-log.md
    closeout.md
document/
deploy/
```

- `RULE.md`: stable project-wide constraints.
- `Issue/README.md`: numbering, lifecycle, ticket index, and Flow index.
- Ticket `README.md`: status, dates, Flow metadata, dependencies, review status, fingerprint, and resolve checklist.
- `spec.md`: SOT, scope, design, acceptance criteria, risk, rollback.
- `discuss.md`: questions and decisions with rationale.
- `diff-note.md`: implemented items, file-to-spec mapping, tests, deviations, out-of-scope findings.
- `review.md`: independent findings, remediation, verification evidence, verdict, and optional reviewed fingerprint.
- `outscope.md`: discoveries intentionally excluded from this ticket.
- `FLOW/<flow-id>/flow.md`: canonical source of truth for one final multi-ticket outcome.
- `current-wave.md`: generated operational queue for in-progress, review, blocked, next executable, and completed tickets.
- `review-queue.md`: generated review debt queue.
- `decision-log.md`: human-maintained Flow-level decisions.
- `closeout.md`: final Flow evidence and decision.
- `document/`: architecture and feature documentation.
- `deploy/`: deployment guides, runbooks, and infrastructure setup.

## 2. Flow model

A Flow represents one final outcome, then organizes Flow/Roadmap, milestones/current wave, tickets, independent review, and closeout.

`flow.md` is the canonical Flow source of truth. Required metadata includes `Flow ID`, `Title`, `Status`, `Owner`, `Created at`, `Updated at`, `Current milestone`, `Required ticket count`, `Completed ticket count`, `Active ticket count`, `Review debt count`, `Blocked ticket count`, and `Final outcome`.

Required human sections include Final Outcome, Definition of Done, Current State, Capability Gaps, Milestones, Ticket Dependency Graph, Active Queue, Completed Tickets, Flow-Level Blockers, and Flow-Level Acceptance Evidence. Generated queue sections are clearly marked and regenerated by `flow-sync`.

Ticket metadata may include `Flow ID`, `Milestone ID`, `Required for flow`, `Dependencies`, `Unlocks`, `Execution order`, `Review status`, `Reviewed change fingerprint`, `Completed at`, and `Blockers`. A ticket may remain standalone or be linked to exactly one Flow. Never silently assign an existing ticket to a Flow.

Dependencies must reference existing tickets, must not self-reference, and must not form cycles. Cross-flow dependencies are rejected unless the workflow is explicitly extended and documented.

## 3. Lifecycle

Ticket lifecycle:

```text
OPEN -> SPEC-READY -> IN-PROGRESS -> IN-REVIEW -> DONE
```

- `OPEN`: ticket exists; discovery/spec work is active.
- `SPEC-READY`: SOT, scope, acceptance criteria, risks, and rollback are agreed.
- `IN-PROGRESS`: implementation is active.
- `IN-REVIEW`: implementation is coherent; targeted evidence and artifacts are ready for review.
- `DONE`: review passes, all required gates pass, metadata is synchronized, and user approval exists.

Move backward only when review invalidates an earlier gate. Explain the reason in `discuss.md`.

Flow lifecycle:

```text
DRAFT -> PLANNED -> ACTIVE -> VALIDATING -> DONE
```

Exceptional states: `BLOCKED`, `CANCELLED`.

Review concepts are recorded as metadata: `REVIEW READY`, `REVIEW IN PROGRESS`, `CHANGES REQUESTED`, `REVIEW APPROVED`, `REVIEW STALE`.

## 4. Gates

### SPEC-READY

- SOT answers what, end-to-end behavior, and exact logic.
- In/out scope are explicit.
- Every acceptance criterion has a verification method.
- Dependencies, risks, migration, compatibility, and rollback are addressed where relevant.

### IN-REVIEW

- Every changed file maps to a spec item.
- Every acceptance criterion has current evidence.
- Targeted tests pass.
- Diff validation and compile/type/lint/contract checks appropriate to the project pass.
- `diff-note.md`, `review.md`, `outscope.md`, and architecture/SOT docs are synchronized.
- Remaining risks and unverified external gates are explicit.

### Ticket DONE

- No unresolved review finding remains.
- Independent review is APPROVED.
- The reviewed change fingerprint matches the current change fingerprint.
- Resolve checklist has no unchecked item.
- Required full-suite gate passes.
- External runtime/deployment evidence required by the spec is terminal and exact-SHA where applicable.
- User has approved the reviewed uncommitted change set.
- One intentional commit may then be created and pushed.

Do not convert local green into a production, database, worker, canary, VPS, or soak claim.

### Flow DONE

Flow DONE requires more than all tickets saying DONE:

- every required ticket is DONE;
- no required ticket has review debt;
- no unresolved BLOCKER or HIGH review finding exists;
- Flow-level acceptance criteria have evidence;
- cross-ticket integration, migration, worker/canary/deployment/soak evidence exists when in scope;
- architecture, source-of-truth, deployment, and rollback documents are synchronized;
- `closeout.md` contains final evidence and an approval decision.

## 5. Review debt and fingerprints

A ticket has review debt when:

- implementation exists but `review.md` is missing;
- review has no final decision;
- review is not independently completed;
- review contains unresolved BLOCKER or HIGH findings;
- acceptance evidence is incomplete;
- code or ticket artifacts changed after the last approved review;
- reviewed fingerprint differs from the current fingerprint;
- review says APPROVED but required test evidence is missing.

After an independent review approves the uncommitted change set, run
`review-freeze`. It writes `reviewed-files.json` with deterministic project-
relative paths, expected presence/deletion, and SHA-256 for every reviewed
file. The deterministic `change_fingerprint` then hashes that manifest, the
current state/content of those exact paths, and normalized current-ticket
artifacts. Ticket text uses normalized line endings; generated metadata,
lifecycle status/dates, and stored fingerprint fields are replaced with stable
markers. The result remains stable across the intentional commit and unrelated
later changes, while any reviewed-file or ticket-evidence change becomes stale.
Before hashing, `review-freeze` materializes all normalized lifecycle fields
(`Unlocks`, `Review status`, `Reviewed change fingerprint`, `Status`, `Done`,
and `Completed at`) so close/link operations only update existing metadata.
Marker strings are part of the fingerprint algorithm and remain stable across
skill upgrades. Human-readable status output must also degrade safely on narrow
Windows console encodings rather than aborting Flow inspection.

Tickets without `reviewed-files.json` retain the legacy `HEAD + diff`
fingerprint only for compatibility. They must receive explicit scope freeze
and independent re-review; never auto-approve historical scope. Use
`--no-discover --path <project-relative-file>` for already committed reviewed
files and `--allow-empty` only when review genuinely covers ticket evidence
without product files. Auto-discovery excludes Issue/Flow roots, while an
explicit `--path` may include a non-generated governance artifact when that
cross-ticket file is intentionally part of the reviewed scope.

## 6. Commands

```powershell
python <skill>/scripts/ticket_tool.py init --project <project-path>
python <skill>/scripts/ticket_tool.py init --project <project-path> --merge
python <skill>/scripts/ticket_tool.py new --project <project-path> --title "<title>"
python <skill>/scripts/ticket_tool.py close --project <project-path> --ticket TD000001
python <skill>/scripts/ticket_tool.py review-freeze --project <project-path> --ticket TD000001
python <skill>/scripts/ticket_tool.py flow-new --project <project-path> --title "<flow title>"
python <skill>/scripts/ticket_tool.py flow-link --project <project-path> --flow FL000001 --ticket TD000002 --milestone M1 --depends-on TD000001
python <skill>/scripts/ticket_tool.py flow-sync --project <project-path> --flow FL000001
python <skill>/scripts/ticket_tool.py flow-status --project <project-path> --flow FL000001
python <skill>/scripts/ticket_tool.py review-queue --project <project-path> --flow FL000001
python <skill>/scripts/ticket_tool.py flow-audit --project <project-path> --flow FL000001
python <skill>/scripts/ticket_tool.py flow-close --project <project-path> --flow FL000001
```

`flow-sync` is deterministic and idempotent. It reads linked tickets, validates dependencies, detects review debt and stale reviews, recalculates progress, computes next executable tickets, moves DONE tickets out of active queues, preserves completed history, regenerates generated Flow files, and updates `Issue/README.md`.

## 7. Review and commit protocol

1. Build one coherent uncommitted change set.
2. Run targeted verification and present diff summary, evidence, assumptions, risks, and remaining external gates.
3. If review finds a defect, amend the same change set and rerun affected checks.
4. After explicit approval, run required full-suite and deployment gates.
5. Commit once with intentional scope and push only when authorized.
6. Test uncommitted code on remote infrastructure only in an isolated review workspace; never replace the active release.

## 8. Multi-repository work

Give each repository its own counter. For work spanning backend and frontend:

- open one ticket per repository;
- cross-link ticket IDs in `Related`;
- keep acceptance criteria owned by the repository that can verify them;
- add an integration gate that names both tickets and the contract version.

## 9. Adoption checklist

1. Run `init`.
2. Tailor `RULE.md` paths and project-specific gates.
3. Add existing SOT, architecture, deployment, and test commands.
4. Decide who can approve `SPEC-READY` and `DONE`.
5. Open a small pilot ticket with `new`.
6. Run `audit` before the first closeout.
7. Add `audit` to CI after the team accepts the workflow.

## 10. Example Flow

Flow `FL000001`: DB-managed Market Hub worker authentication.

Final outcome: a newly created bot can start and authenticate with Market Hub without adding a per-bot credential to ENV.

Milestones:

| Milestone | Outcome | Tickets |
| --- | --- | --- |
| M1 | Database contracts | TD000101, TD000102 |
| M2 | Token services | TD000103, TD000104 |
| M3 | Runtime integration | TD000105, TD000106 |
| M4 | Migration and cutover | TD000107 |

Current wave after `flow-sync`:

- IN PROGRESS: TD000104.
- WAITING FOR REVIEW: TD000105.
- RE-REVIEW REQUIRED: TD000106 because its fingerprint changed after approval.
- BLOCKED: TD000107 because TD000105 is not DONE.
- NEXT EXECUTABLE: TD000103 because all dependencies are DONE and reviewed.
- RECENTLY COMPLETED: TD000101, TD000102.

Closing reviewed TD000103 moves it to completed, updates progress, removes it from current work, unlocks TD000104 if its other dependencies are done, and regenerates both current wave and review queue. No ticket folder, spec, diff note, review report, out-of-scope report, test evidence, or architecture traceability is physically deleted.
